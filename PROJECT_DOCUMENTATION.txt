NEXUSPAY BANKING APPLICATION
PROJECT DOCUMENTATION
Updated: October 2026

1. PROJECT SUMMARY

NexusPay is a cross-platform banking and fintech project with a React web interface and an Express API written in TypeScript. The active backend uses PostgreSQL for identity and financial records, and MongoDB for notification and activity-log documents.

The API supports registration, login, password reset, account management, beneficiary management, internal transfers, transaction history, notifications, and transaction search. Registration creates a user and a default USD account in PostgreSQL. Existing SQLite and MySQL accounts are not imported.

2. TECHNOLOGY STACK

Frontend
- React 19, TypeScript, and Vite
- Wouter for client-side routing
- React Hook Form and Zod for forms and validation
- Recharts for charts; Lucide React for icons
- Tailwind CSS and Radix-based UI components

Backend
- Node.js, Express 4, and TypeScript
- Sequelize 6 with the PostgreSQL driver (`pg`)
- Mongoose 9 for MongoDB documents
- Zod request validation, bcryptjs password hashing, and JSON Web Tokens
- Nodemailer for password-reset and OTP email; Swagger UI for API documentation

Databases
- PostgreSQL 16: users, accounts, beneficiaries, transactions, ledger entries, sessions, OTP challenges, and outbox events
- MongoDB 7: notifications and activity logs

3. DATA OWNERSHIP AND DESIGN

PostgreSQL is the source of truth for user identity and all financial balances and records. The PostgreSQL schema uses UUID primary keys, foreign keys, NUMERIC monetary values, account balance checks, uniqueness constraints, and indexes. Transaction search uses PostgreSQL full-text search with a `tsvector` column and GIN index.

MongoDB stores flexible notification and audit activity documents. Mongo document `userId` fields contain the corresponding PostgreSQL UUID as a string. Notifications support read, archive, priority, and optional expiration fields. Activity logs include event category, metadata, and request context where available.

The backend does not use SQLite or MySQL. Old local SQLite files, if present, are not read, migrated, or deleted by this project.

4. POSTGRESQL TRANSACTION FLOW

The PostgreSQL transfer service validates positive monetary values and checks account ownership, recipient existence, account currency, self-transfer, and idempotency. Within a PostgreSQL transaction, it creates the transaction row, locks the sender and recipient account rows in a deterministic order, checks the sender balance, updates both balances, writes a debit and credit ledger entry, marks the transaction complete, and inserts an outbox event.

The database transaction keeps balance updates, ledger entries, and the completed transfer record atomic. Monetary values are handled as decimal strings using `decimal.js` and PostgreSQL NUMERIC columns rather than JavaScript floating-point arithmetic.

The `/api/transactions/v2/transfer` route supports configurable email OTP confirmation when the amount reaches `TRANSFER_MFA_THRESHOLD` and `MFA_ENABLED` is true. The regular `/api/transactions/transfer` route also calls the PostgreSQL transfer service. The outbox worker processes queued events; MongoDB remains the store for notifications and activity logs.

5. AUTHENTICATION AND SECURITY

- Passwords are hashed with bcryptjs; they are never stored as plaintext.
- Login and registration issue short-lived access tokens. The refresh token is stored as a hash in PostgreSQL and returned to the browser in an HttpOnly cookie.
- Refresh requests rotate the token. Logout revokes the corresponding PostgreSQL session.
- Password-reset tokens are hashed before being stored and expire after one hour.
- Request bodies and query parameters use Zod validation. Authentication, transfers, and general API requests use rate limiters.
- Helmet and configured CORS middleware protect the HTTP API.
- Larger v2 transfers can require a six-digit email OTP. OTP hashes, expiry, purpose, and attempt counts are stored in PostgreSQL.

Configure database credentials and token secrets through `.env`; use `.env.example` as the template. Production deployments should replace all sample secrets and database passwords with private values.

6. BACKEND STRUCTURE

backend/index.ts                  Express entry point, initialization, and v2 routes
backend/config/env.ts             Required environment configuration and validation
backend/config/swagger.ts         OpenAPI documentation setup
backend/db/postgres.ts            PostgreSQL connection and migration runner
backend/db/migrations/            PostgreSQL schema migration
backend/db/pg-models/             Sequelize models for PostgreSQL tables
backend/db/mongodb.ts             MongoDB connection setup
backend/db/mongo-models/          Mongoose notification and activity-log models
backend/routes/                   Authentication and resource routes
backend/services/                 Authentication, transfer, account, notification, and search logic
backend/middleware/               Authentication, security, and rate limiting
backend/validation/               Zod API schemas
client/src/                       React application and UI components

At startup, the server validates configuration, connects to PostgreSQL and MongoDB, and applies `backend/db/migrations/002_postgres_schema.sql` once. Applied migration names are stored in the PostgreSQL `schema_migrations` table. The migration is also run for the application container; database container initialization does not depend on a mounted schema file.

7. API REFERENCE

All routes are under `/api`. Routes marked authenticated require an `Authorization: Bearer <access-token>` header.

Authentication
- POST `/auth/register` — register a user and create a default USD account
- POST `/auth/login` — authenticate and issue tokens
- POST `/auth/refresh` — rotate the refresh token cookie
- POST `/auth/logout` — revoke the current session; authenticated
- POST `/auth/forgot-password` — request a password-reset email
- POST `/auth/reset-password` — reset the password using a valid token
- GET `/auth/me` — return the authenticated user

Accounts (authenticated)
- POST `/accounts` — create an additional currency account
- GET `/accounts` — list the user's accounts
- GET `/accounts/:id` — retrieve an account owned by the user
- GET `/accounts/:id/balance` — retrieve the account balance

Transactions (authenticated)
- POST `/transactions/transfer` — execute an internal transfer
- POST `/transactions/v2/transfer` — PostgreSQL transfer endpoint with idempotency, ledger, outbox, and threshold-based OTP support
- GET `/transactions` — paginated transaction history
- GET `/transactions/:id` — currently returns HTTP 501; single-transaction lookup is not implemented
- GET `/transactions/search-fts?q=...` — PostgreSQL full-text transaction search

Beneficiaries (authenticated)
- POST `/beneficiaries` — add a beneficiary
- GET `/beneficiaries` — list beneficiaries
- GET `/beneficiaries/:id` — retrieve a beneficiary
- PUT `/beneficiaries/:id` — update a beneficiary
- DELETE `/beneficiaries/:id` — remove a beneficiary

Notifications and search (authenticated)
- GET `/notifications` — list notifications with pagination and unread counts
- POST `/notifications/:id/read` — mark one notification read
- POST `/notifications/read-all` — mark all notifications read
- DELETE `/notifications/:id` — archive a notification
- GET `/search?q=...` — search transaction records in PostgreSQL

Operations
- GET `/health` — report PostgreSQL and MongoDB connection status
- GET `/docs` — Swagger UI
- GET `/docs.json` — OpenAPI JSON

8. FRONTEND STATUS

The client contains login, sign-up, forgot-password, reset-password, and dashboard screens. `AuthContext` calls the API's login and registration endpoints. The dashboard currently presents example banking data in the UI; account, transfer, beneficiary, notification, and search API routes are implemented in the backend, but the dashboard is not currently wired to those resource endpoints.

9. LOCAL DEVELOPMENT

Requirements: Node.js 20 or newer, pnpm, and Docker Desktop.

1. Copy `.env.example` to `.env` and set PostgreSQL credentials plus private JWT and cookie secrets.
2. Start PostgreSQL and MongoDB from the project directory:

   docker compose -f docker-compose.dev.yml up -d

3. Install packages and start the web client and API:

   pnpm install
   pnpm dev

The Vite client uses port 3000 and the API uses port 3001 in local development. The API health endpoint is `http://localhost:3001/api/health`; Swagger UI is `http://localhost:3001/api/docs`.

10. DOCKER DEPLOYMENT

The default `docker-compose.yml` starts the production API, PostgreSQL, and MongoDB. Set secure values for `PG_PASSWORD`, `JWT_SECRET`, `ACCESS_TOKEN_SECRET`, `REFRESH_TOKEN_SECRET`, and `COOKIE_SECRET` in `.env`, then run:

   docker compose up -d --build

The application and API are served on port 3000. PostgreSQL is exposed on port 5432 and MongoDB on port 27017. Named volumes persist database data. `docker compose down` stops the services without removing those volumes.

11. PROJECT LIMITATIONS AND DATA TRANSITION

- No automatic migration from the previous SQLite or MySQL account stores is included. Users must register again in PostgreSQL; existing local database files are left untouched.
- The dashboard still uses example data and does not yet display live account or transaction API results.
- The single-transaction lookup endpoint is not implemented and returns HTTP 501.
- Transaction full-text search is backed by PostgreSQL. It does not search MongoDB notifications or activity logs.
- An available API endpoint does not by itself demonstrate production readiness. Production deployment still requires private credentials, configured email delivery, operational monitoring, and environment-specific review.
